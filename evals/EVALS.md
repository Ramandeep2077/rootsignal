## Methodology and caveats

- **Synthetic data.** 12 simulator scenarios with known root causes (see `docs/scenarios.md`). Each run uses a different seed, so noise, timings and red-herring changes differ between runs. Results say how the system does on these scenarios, not on real production incidents.
- **Real pipeline.** Alerts go over HTTP to the Java alert service, through Kafka (Redpanda), to the agent service (run in-process by the harness so the model profile can be switched), which uses the MCP servers and local Ollama models, writes back over HTTP, and notifies the mock Slack webhook.
- **Exact match** compares the predicted category with the label. **LLM-as-judge** (`qwen2.5:7b`, temperature 0, rubric in `evals/src/rootsignal_evals/judge.py`) grades the free-text hypothesis 1-5 against the ground-truth explanation. A local 7B judge is weaker than a frontier model, so treat it as a second opinion next to exact match.
- **Rules-only baseline.** The heuristic investigator was written knowing the simulator's log vocabulary, so its accuracy is an optimistic upper bound for keyword matching, not a fair competitor. It's included to show the latency/cost floor and what the LLM adds beyond keywords.
- **Time to summary** runs from the first alert reaching the alert service to the analysis being stored. It includes the ~6-20 s grouping window and CPU/iGPU inference on one laptop, with other workloads running.
- **Action accuracy** counts a proposal as correct when it is one of the scenario's expected runbook actions. A few actions (e.g. `enable_circuit_breaker`, `scale_out`) appear in several runbooks, so an action can be acceptable even when the diagnosis is wrong; read it together with category accuracy.
- **Cost** is $0 because the models run locally; token counts are reported so hosted-model cost can be estimated with any price list.
